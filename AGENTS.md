# AGENTS.md

## Project shape

- This is a Bun-run TypeScript blockchain node with no root workspace config. The root lockfile is intentionally ignored; `explorer/` and `wallet/` are independent Vite/React packages with their own `bun.lock`. Install the root, then run `bun install` in each UI directory. `apps/miner-rs/` is a standalone Cargo crate whose `Cargo.lock` **is** committed.
- The node network surface is HTTP JSON-RPC, external miners, and an **opt-in** P2P layer under `src/p2p/` (TCP, Bitcoin-style gossip — see the "P2P layer" section below). P2P is **off by default** and starts only when `NEX_P2P_ENABLED` is truthy, so a single-node dev setup behaves exactly as before. There is no node keypair or identity: peers are addressed by `host:port` and blocks are unsigned (PoW + hash chain only).
- `apps/node/server.ts` is the node entrypoint (`bun run node:start`, which runs `bun run apps/node/server.ts`) and serves JSON-RPC at `POST /rpc`; it attempts to create genesis on startup when the chain is empty. `apps/miner-rs/` is the **only** external miner (`bun run miner:rs -- --address NxC…`, a wrapper for `cargo run --release`). There is no Bun/TypeScript miner any more — do not reintroduce one.
- The shared/core modules now live under `src/`: `src/core/` (the blockchain engine — was `nexchain/`), `src/core/state/account/` (ledger account state: `getAccount`/`putAccount` — was `wallet/balance/`), `src/crypto/` (key + sign), `src/client/`, `src/types/` (was `interface/`), `src/logging/`, and `src/rpc/`. Runnable apps live under `apps/`: `apps/node/` (the node) and `apps/miner-rs/` (the Rust miner). `explorer/` (Vite port 5173) and `wallet/` (port 5174) are independent frontends; the root `tsconfig.json` excludes both.
- **The node has no wallet, account, or balance of its own.** There is no node mnemonic file, no `wallet.conf.json`, and no `nex_createWallet` RPC — all of that was removed because a node that signs or holds keys contradicts the design. Genesis pays its reward to a burned address, and mining is keyless: the miner supplies `minerAddress` to `nex_getWork` and the coinbase pays that address. `src/core/state/account/` is the _ledger_ (every address's balance), not the node's own account; do not conflate the two. Keys live only in clients (the browser wallet vault in `src/client/wallet/`).
- Mining is intentionally outside the node: the miner gets `nex_getWork`, hashes the payload and nonce, then submits `nex_submitWork`; the node verifies the work (blocks are unsigned — Bitcoin-style PoW, the node holds no key). The miner needs only the RPC URL and reward address. There are **two** copies of the consensus rules that matter to mining — node (`src/core/`) and `apps/miner-rs/` (Rust) — and the parity vectors are the guard: `cargo test` in `apps/miner-rs/` hardcodes hashes generated from `node:crypto`, so a drift shows up as a red test instead of a submit the node silently rejects. Synchronize both when `src/core/consensus/` changes.

## Commands

- `bun run check` is the root `bunx tsc` typecheck, then deletes `dist` on success; `bun run build` emits root `dist`. Neither runs the regression gates or either UI.
- Rust miner: `bun run miner:rs -- --address NxC...` (wrapper for `cargo run --release --manifest-path apps/miner-rs/Cargo.toml --`). Its tests are `cargo test` **inside `apps/miner-rs/`** and are not part of `check:all` (no Rust toolchain in the gate path); run them by hand after touching any mining rule.
- Core gates: `bun run check:browser`, `bun run check:tx`, `bun run check:wallet`, `bun run check:difficulty`, `bun run check:pow`, `bun run check:journal`, `bun run check:state`, `bun run check:reorg`, `bun run check:log`, and `bun run check:p2p`. `check:log` proves the file sink on a temp directory: the pure parts (`logFileName`, `stripAnsi`, `pruneOldLogs` retention = keep `days` days _including_ today, ignore non-matching names), that a `debug` line still reaches the file while being suppressed on a quiet console, that a logger line is not duplicated by the `process.std*.write` patch, and that a half-line chunk is never flushed as its own line. The browser gate checks bundling, tx/difficulty/p2p are offline, and the wallet gate uses memory plus `fake-indexeddb` without needing a node. `check:p2p` covers framing, `parseMessage`, the `MAX_INV_BATCH` limit, per-kind tx/block hash shape, config parsing (incl. the `syncTimeoutMs` floor), handshake identity checks, the ban list, the broadcast gate, the IBD sync-state module (incl. the M2 `forked` phase), the neutral peer snapshot (`src/core/events/peerState.ts`, the data behind `nex_getPeerInfo`), the serve-pacing helper `src/p2p/scheduling.ts` (`yieldToLoop` hands off a macrotask; `forEachChunked` yields between chunks, not after the last item, clamps an invalid `chunkSize` to 1, and stops on `visit → false`), the **block codec** v2 round-trip (`encodeBlock`/`decodeBlock` on the real genesis block and on a block with a real signed transaction — asserting `prepareBlockForHashing` is byte-identical, not just field-equal, plus `size` float, `difficulty` float (0.25-bit quantization), `metadata` absence, a `TxC…`-style `merkleRoot`, malformed payload rejection, and a 1 MiB base64 payload that would have blown `String.fromCharCode(...)`), and a source scan proving `src/core/**` never imports `src/p2p/**`; it prints expected `parsePeerList` warnings on stderr. `check:reorg` proves the M2 reorg machinery on real LevelDB with fake-but-consistent hashes (`commitBlock` verifies neither PoW nor the block hash): pure fork choice (`Σ 2^difficulty`, not height), the in-memory branch pool (cap/evict), common-ancestor tracing, a full reorg (tip/state/balances equal a fresh one-node chain, orphaned txs re-added), a lighter branch leaving the tip untouched, the `MAX_REORG_DEPTH` (128) rejection, and `invalidateFrom` (R-1). It also covers S4: the incremental-verification marker's set/get/invalidate/reset semantics, the incremental path on a genesis-only chain, fallback to full verification when the marker is stale (hash mismatch), a **real-PoW** block proving `verifyChainIntegrity` (full) and `verifyChainIncremental` (suffix) agree, a negative control (a fake-hash block rejected by both paths), and the reorg re-seed of the marker to the fork block. `bun run p2p:smoke` spawns three localhost nodes on fixed ports (RPC 18501/18502/18503, P2P 30501/30502/30503), mines one block on the first, asserts the second syncs height+hash, that `nex_getPeerInfo` on the first reports the handshaked peer, relays a transaction to the second's mempool, asserts the third (pointed at a dead peer) refuses `nex_getWork` until the IBD safety valve opens (~90s+, mutates only temp data dirs), and ends with a socket-only reconnect check that a bootstrap seed given as a **hostname** is re-dialed after the connection drops (this is `PeerConnection.dialKey`: the outbound endpoint key must be the configured `host:port`, never `remoteAddress`, which is the DNS-resolved IP — using the latter strands the `outbound` map entry and silently kills reconnect forever). `bun run p2p:fork` covers the one thing no offline gate can: a **live reorg**. Two nodes boot isolated from the same deterministic genesis (a fresh chain always has 20-bit difficulty and the second block climbs to 22 bits — `MAX_RISE_BITS`), mine separate branches (A two blocks, B one), then B is restarted **on the same data dir** pointed at A. Fork choice (`Σ 2^difficulty`) must make B reorg onto A's heavier branch, A must refuse B's lighter one, and both tips must end identical. It asserts the fork is real (the two height-1 blocks share the genesis parent but differ), and it is the gate that caught `header.difficulty` being encoded as an integer when `clampDifficulty` quantizes to 0.25-bit steps. Its PoW budget is ~4× a normal block, so it mines with `JOB_TTL_MS` rather than the tighter default. `bun run p2p:evil -- <scenario> --host <h> --port <p>` sends a malicious peer against a live node (observation-only, always exits 0). `check:pow` proves `PowHasher` (the fixed-buffer PoW hot path) is byte-for-byte identical to `hashWithNonce` and to `node:crypto`, including UTF-8/non-ASCII payloads and huge nonces. `check:tx` asserts the localhost default, so unset `NEX_RPC_URL` (including a value loaded from `.env`) before running it. `check:browser` ends with POSIX `rm -f`; verify cleanup on Windows if the shell does not provide it. `bun run pow:bench` is a diagnostic (not a gate) that compares old-vs-new hash paths and shows how throughput scales with worker count on the current machine — a rough reference before choosing `--threads` for the Rust miner.

## PoW hot path

- The mining loop is the one place where hashing cost matters, so the canonical modules expose a bulk API: `createPowHasher(payload).hash(nonce)` (in `src/core/encoding/sha256.ts`, re-exported from `src/core/consensus/Pow.ts`). It encodes the payload once and writes each nonce into a fixed buffer, avoiding the per-iteration string concat in `hashWithNonce`. Use `hashWithNonce` for one-off hashing only (e.g. node re-verification); use `createPowHasher` inside any mining loop.
- **Chain-verification hot path (S4).** `nex_getWork` calls `isChainsValid()` before building work. Since S4 that routes to `verifyChainIncremental()` (`src/core/consensus/verify/verifyIntegrity.ts`), which verifies only the suffix above an in-memory **hash-keyed** marker (`src/core/consensus/verify/verifyMarker.ts`) instead of the whole chain from genesis — the old O(N)-per-poll cost. Both paths share the single `verifyRange` loop, so full and incremental results are identical by construction. No marker (boot / after reorg) or a stale marker (block at that height changed) falls back to full `verifyChainIntegrity()` (fail-closed). Reorg clears the marker via `invalidateVerifyMarkerFrom` inside `invalidateFrom` (R-1) and re-seeds it to the fork block. The marker is memoization, not trust: blocks are content-addressed, verification is deterministic, and every history mutation invalidates it — but it is in-memory only, so it does not catch on-disk corruption that appears after the marker formed (mitigated by the full verify at boot).
- Never replace `Math.floor(n / 10)` with `(n / 10) | 0` when formatting a nonce: `| 0` forces int32 and silently corrupts nonces >= 2^31. `check:pow` guards this with `Number.MAX_SAFE_INTEGER`.
- `apps/miner-rs/` keeps the PoW loop in Rust with a **midstate**: the full payload blocks are compressed once per job (`sha2::compress256`, feature `compress`), so each nonce costs only 1–2 tail compressions. Threads share an `AtomicU64` cursor in chunks of 65 536 nonces (load-balanced, no static partition) and a stop `AtomicBool`; the main thread polls `expiresAt` and prints the hashrate every 5 s. Nonces are capped at `MAX_NONCE = 1 << 53` so `nonce.to_string()` is identical to `String(nonce)` in JS. Do **not** write SHA-256 by hand — only the midstate glue and decimal-nonce writing are local code, and `self_check()` at startup compares against hardcoded `node:crypto` vectors (a mismatch exits 1 before mining). `cargo build --release` needs the Rust toolchain, so **no CI gate calls `cargo`**; `bun run miner:rs` forwards args to the binary for convenience. `--once` mines exactly one block and exits (0 = submit accepted, non-zero = rejected) — that is what the `live` gate runs, against the already-built binary. Calibrate `--threads` rather than assuming more is better — throughput saturates and a 4C/8T laptop throttles under sustained load.
- `apps/miner-rs` keeps its own copy of the hashing/format rules (a separate language cannot share code), so `src/core/consensus/Pow.ts` and `apps/miner-rs/src/midstate.rs` must stay in sync when the nonce-formatting rule changes; `cargo test` is the guard.
- Frontends: `bun run explorer:dev`, `bun run explorer:build`, `bun run --cwd explorer typecheck`, `bun run --cwd explorer audit:ui`, `bun run --cwd explorer smoke`; `bun run wallet:dev`, `bun run wallet:build`, `bun run wallet:build:web`, `bun run wallet:preview:web`, `bun run wallet:smoke:pwa`, `bun run wallet:typecheck`, `bun run wallet:smoke`. UI `build` scripts run `tsc --noEmit` before Vite; `audit:ui` is static contrast/class coverage. `explorer smoke` needs a live RPC with at least five blocks; `wallet:smoke` is local and does not touch LevelDB or send transactions.
- There is no `test` or `lint` framework, but there is one aggregate gate: **`bun run check:all`** (`scripts/checkAll.ts`) runs every gate in five phases and fails fast on the first failure, and **`.husky/pre-push` calls it**, so a broken commit never reaches GitHub. Phases: `offline` (`check`/tsc + every `check:*` + `wallet:smoke:pwa`, which builds the PWA target and verifies the artifacts + `genesis:check`), `local` (`wallet:smoke`), `p2p` (`p2p:smoke`, which spawns three nodes itself, then `p2p:fork`, which spawns two isolated nodes and joins them to prove a live reorg), `live` (miner Rust `--once` against one ephemeral node on a temp data dir + free port with empty RPC credentials and P2P off, so **no node has to be started by hand** — the gate runs the **already-built** `apps/miner-rs/target/release/nex-miner` and is **skipped with a warning** when that binary is absent, because no gate calls `cargo`), and `explorer` (`explorer smoke` — reuses an **existing** node, URL from `NEX_EXPLORER_RPC_URL` else `explorer/.env`'s `VITE_RPC_URL`; **skipped with a warning, not failed**, when that node is unreachable or has fewer than five blocks). `NEX_CHECK_FAST=1` runs only `offline`, `NEX_CHECK_PHASES=<list>` selects phases (debug), and a one-off bypass is `git push --no-verify` or `HUSKY=0 git push`. Bumping the gate list means editing `OFFLINE_GATES` in `scripts/checkAll.ts`. The Husky `pre-commit` hook is still only a shebang (there are no GitHub workflows). `scripts/vaultBench.ts` is a benchmark, not a correctness test; `scripts/e2ePostRemoval.ts` mutates a funded live node (mempool, balances, and chain) and currently spawns a missing `mine.ts`, so neither is a routine check.
- Formatting is `bun run format` (Prettier: tabs, no semicolons, single quotes, trailing commas, width 80); use focused `bunx prettier --write <files>` when possible.

## RPC contracts

- All RPC results are now plain JSON (no hex envelope); explorer/mempool/peer methods were already plain. When adding or changing a method, update the matching decoder in `explorer/src/api/methods.ts` and the relevant smoke coverage.
- Two traps worth repeating for miner clients: `nex_getWork`/`nex_submitWork` return plain JSON, and `nex_getWork` echoes `minerAddress` plus an `expiresAt` epoch-ms the client should count down (`JOB_TTL_MS` is 5 minutes in `src/core/consensus/jobStore.ts`).

## P2P layer (`src/p2p/`)

- Opt-in TCP peer network used to chain-sync a joining node and gossip blocks/transactions. Modeled on early Bitcoin, not Ethereum devp2p: no node identity, no signing; peers are `host:port` and blocks are unsigned PoW. It is a **consumer** of `src/core/` (like `src/rpc/`), never the reverse — core publishes through the neutral bus `src/core/events/nodeEvents.ts` (`publishBlock` after a mining commit in `src/core/consensus/work.ts`, `publishTx` on mempool admission in `src/core/transaction/addTransactionToMempool.ts`), and `src/p2p/node.ts` subscribes and broadcasts. Core must never import `src/p2p/`.
- Secure-by-default: disabled unless `NEX_P2P_ENABLED` is truthy, binds `127.0.0.1` by default (`NEX_P2P_BIND_HOST`), and has **no authentication** — treat a non-loopback bind like exposing the RPC write surface. `startP2P()` warns on a non-loopback bind. All `NEX_P2P_*` variables are documented in `.env.example`.
- Wire format is a 4-byte big-endian length prefix + UTF-8 JSON (`src/p2p/transport/framing.ts`; `parseMessage` is fail-closed). Protocol **v0.1 (wire `0`)**: `version`/`verack` (handshake checks chain id + genesis hash, mismatch is fatal → ban), `ping`/`pong`, `getblocks`/`inv`/`getdata`/`block` (base64 RLP via `encodeBlock`), `tx` (base64 RLP via `encodeTx`). Block and tx bodies are **not** raw JSON any more: `block.payload` is `base64(rlp(block))` (schema `src/core/encoding/rlp/blockCodec.ts`, wrapper `src/core/encoding/hex/block/`) and `tx.payload` is `base64(0x02 ‖ rlp(signed))`. `decodeBlock` rejects a malformed payload hard and `syncManager` treats that as a wire violation → ban. Every bump so far is **breaking with no down-negotiation** (`P2P_PROTOCOL_VERSION` lives only in `src/p2p/protocol/messages.ts`; v1→v2 changed the wire bodies, v2→v3 (C1) changed block verification, v3→v0.1 changed the address shape — see below), so every node and every `NEX_P2P_PEERS` peer must upgrade together. Three block fields bite when encoding: `size` is a number (since A4 it is the Σ `encodeTxPayload` byte count of the block's user txs, 0 for genesis — outside the PoW preimage, **verified since C1**: `verifyStruct` recomputes the Σ from `transactions` and rejects any mismatch, plus hard caps `MAX_BLOCK_WIRE_BYTES` and `MAX_TX_PER_BLOCK` in `src/core/consensus/blockLimits.ts`, which is why pre-A4 data dirs must be wiped and protocol bumped) that still rides as raw float64 big-endian, `difficulty` is **also a float** (`clampDifficulty` quantizes to 0.25-bit steps, so 21.5 is legal on a real chain) and would be rejected by an integer encoding — which silently kills block relay, as `p2p:fork` proved, and `merkleRoot` is a plain string that is 64-hex **or** `TxC…` for a single-tx block — never assume hex64. `coinbaseTransaction` key order is consensus (`JSON.stringify` feeds the PoW preimage), so the codec reproduces the `amount, receiver, extraData` order used by `genesis.ts`/`createBlockTemplate.ts`; `txToRlpList`/`rlpListToTx` are reused through `encodeTxPayload`/`decodeTxPayload` so `from`/`txHash` (which `verifyStruct` requires) are recomputed. Peer manager owns handshake/keepalive/ban/maxPeers; sync manager owns `getblocks`/`inv`/`getdata`/`block`/`tx`; `src/p2p/broadcastGate.ts` and `runSuppressed` prevent gossip loops by suppressing the core-bus broadcast while an inbound item is being handled.
- **Reorg is supported (M2).** `src/p2p/validation/connectBlock.ts` has two paths: a block that extends the tip (`height === tip.height + 1` AND `previousBlockHash === tip.hash`) is committed directly; any other block is verified against its parent and parked in the in-memory branch pool (`src/core/consensus/reorg/`), which re-evaluates work-based fork choice (`Σ 2^difficulty`, not height) and reorgs only if the branch is heavier and within `MAX_REORG_DEPTH` (128). It never re-commits a block that already exists (a second `commitBlock` would re-run `processTransact` and double-credit balances). Consensus violations (struct/PoW/hash/merkle/reward/timestamp/difficulty) are fatal → ban; tip-link mismatches and duplicates are non-fatal → ignored. It reuses `src/core/consensus/verify/module/*` rather than duplicating rules.
- Observability & relay: `nex_getPeerInfo` returns a plain-JSON peer snapshot written by `peerManager` into the neutral `src/core/events/peerState.ts` (same dependency direction as `syncState.ts`). `syncManager` re-announces the whole mempool (`inv` of tx hashes) on peer handshake and every 60s, so a node that connects after a tx was admitted still learns it. Module map: `src/p2p/README.md`.

## Runtime and data

- Copy the root `.env.example` to `.env`. `apps/node/server.ts` loads the working-directory `.env`; `NEX_RPC_PORT` (or `PORT`) defaults to 8000; `RPC_BIND_HOST` defaults to `127.0.0.1` when unset (`process.env.RPC_BIND_HOST as string || '127.0.0.1'`), so a localhost-only node needs no explicit setting — use `0.0.0.0` only when another LAN host must reach the RPC. Write methods (`nex_sendTransaction`, `nex_sendRawTransaction`, `nex_getWork`, `nex_submitWork`) are Basic-Auth protected: they require HTTP Basic credentials from `RPC_USER`/`RPC_PASSWORD` when those are set, are loopback-only when they are unset, and the node refuses to start on a non-loopback bind without them (`src/rpc/authLogic.ts`, gate `bun run check:rpc`).
- The shared Node/Bun client uses `NEX_RPC_URL` (default `http://localhost:8000/rpc`); the Rust miner (`apps/miner-rs/`) reads the same variable, defaults to that URL, and takes `--rpc` for an explicit override (it never prompts for the URL). Vite apps use build-time `VITE_RPC_URL`; wallet also accepts optional `VITE_EXPLORER_URL` (or a Settings/localStorage override) for confirmed transaction links. Explorer requires `explorer/.env`; wallet env is optional, with runtime priority `localStorage` override → `VITE_RPC_URL` → page-host fallback.
- **Boot replays the state (v0.1).** Every header commits a `stateRoot`, so `apps/node/server.ts` runs `replayState()` after genesis verification: it rebuilds the state from genesis, checks each block's root **and** compares the stored accounts against the replay, and exits non-zero on any mismatch (fail-closed) instead of serving balances that were never committed. `--rebuild-state` rewrites the state from the blocks (stale accounts deleted) once the operator is sure the chain is right. The incremental path `nex_getWork` uses does **not** replay. Adding a state writer means routing it through `putAccount`/`saveTxHistory`/buffer, or the replay diff will reject the node at boot.
- **Addresses and storage keys (v0.1).** An address is `NxC` + 40 lowercase hex (43 chars) and encodes to **20 bytes** — the old `NxS` prefix and the 1-byte address tag are gone, so `addressToBytes`/`bytesToAddress` (`src/core/encoding/rlp/codecScalars.ts`) and the Rust miner's `is_valid_address` accept only `NxC`. Mempool entry keys are the `txHash` verbatim (`TxC` + 64 hex, one range `TxC`..`TxD`, no `0x` prefix and no legacy fallbacks). Address history is one entry per (address, tx): `addr:<address>:<height 8-digit>:<txHash>` → `in`/`out`/`self`, read as a reverse range scan.
- Level stores live under the data directory resolved by `NEX_DATA_DIR` (default `./data`, relative to the working directory), one LevelDB per store: `{block,history,journal,memPool,state,storeData}` (six). `journal` is the undo journal / write-ahead log — see `src/core/state/journal/README.md`. The path is deliberately anchored to `process.cwd()` and **not** to `__dirname` (see `src/core/state/db/dataDir.ts`): a source-relative path silently relocates the chain when the code moves or is bundled, and it puts chain data inside the source tree. `initFile()` is fail-closed — it probes writability and throws rather than letting the node start against a data directory it cannot write. Do not commit `data`, `config`, `logs`, or `dist`.
- **Logging is split: a quiet console, a complete file.** The console shows only milestones and errors; `debug`-level lines appear only when the node is started with `--debug`. The file always gets everything, including those unsuppressed-on-console `debug` lines — so a detail you did not see live is still recoverable afterwards. `src/logging/fileSink.ts` is the one sink: `installFileLogging()` is called once as the first statement of `apps/node/server.ts`, it captures the ORIGINAL `process.stdout.write`/`process.stderr.write` and patches them so that anything printed _outside_ the logger (third-party output, stack traces) is also appended, while `emit()` prints through the saved originals — so a logger line is never recorded twice, **by construction rather than by comparing text**. Files are per UTC day (`nex-YYYY-MM-DD.log`), appended with `appendFileSync` (no open handle, crash-safe), resolved against `process.cwd()` via `NEX_LOG_DIR` (default `./logs`) — the same anti-`__dirname` principle as `dataDir.ts`. Retention is `NEX_LOG_RETENTION_DAYS` (default 3) and means "keep the last N days _including_ today"; pruning runs at install and at every date rollover. Setting up the log files is deliberately **best-effort**, unlike the fail-closed data dir: a read-only or full log directory prints one warning and the node keeps running (losing mining to an unwritable log dir would be far worse). **The browser constraint is real here:** `logging.ts`/`debug.ts`/`errorLog.ts` are reachable from `scripts/browserWalletEntry.ts` (via `src/crypto/processPubKey.ts`) and `src/logging` is in the UI `ROOT_MODULES`, so they must never statically import `node:fs`/`node:path` — load them with the same non-literal dynamic-specifier trick `errorLog.ts` uses; `bun run check:browser` is the guard.
- **Name clarification:** the `wallet/` directory at root is the **UI package** (browser wallet source). It is unrelated to any node account — the node has no wallet, no mnemonic, and no `wallet/main.json`. The `.gitignore` entry `/wallet/*` with explicit `!/wallet/src/` etc. whitelists only ignores untracked files inside the UI package folder (e.g. accidental local build artifacts), never the source itself.
- The node has no wallet and holds no keys. Genesis reward is sent to a burned address, and mining is keyless: the miner supplies `minerAddress` to `nex_getWork` and the coinbase pays that address. The node only verifies work; it never signs anything.

## Shared browser code

- `wallet` aliases the backend modules through its `vite.config.ts` (`ROOT_MODULES` maps `src/core`, `src/crypto`, `src/types`, `src/client`, `src/rpc`, `src/logging`) rather than duplicating crypto and transaction logic. `apps/miner-rs/` deliberately does not alias anything — it is a separate language and keeps its own copies, guarded by parity tests. When a new backend module under `src/` must be consumed by a UI, add it to that app's `ROOT_MODULES` and to its `tsconfig.json` `paths`.
- New contributors should start with `docs/LEARNING_PATH.md`; each module carries a short `README.md` explaining its responsibility and entry points.
- Keep shared browser imports free of Node built-ins; `bun run check:browser` is the guard. Keep `wallet/src/polyfill.ts` imported before wallet modules, preserve the Vite `buffer` alias, and use named `bip39` imports (the default import breaks Vite interop).
- Wallet amounts use `formatNxcCompact()`/`AmountDisplay` for primary UI; keep exact nexu values only behind the detail disclosure so mobile layouts stay readable.

## wallet/ — one codebase, several shells

- `wallet/` is not a single app. `wallet/src/` is the shared source (nine screens, `ui/`, `lib/`, `workers/`, `pwa/`) and `wallet/shells/` holds the entry points. `wallet/src/lib/vaultStore.ts`, `deviceCrypto.ts`, `rpcUrl.ts`, and `platform.ts` are the **four injection points** where shells differ; the screens never branch on platform. Adding a shell means writing a new entry under `shells/` that injects a `WalletKV`, a device class, an RPC default and (optionally) a `PlatformBridge`, then renders the shared `App`. `platform.ts` is pure presentation state (installed / can-install / persistence / update-available): dev and desktop never install a bridge, so `supported === false` and the Settings "Aplikasi" card and update banner simply do not render — that is why the desktop build never resolves `virtual:pwa-register`.
- Shells: `shells/dev/` (Vite port 5174, memory vault via an explicit `installVaultKV(createMemoryKV())`, for working on the UI), `shells/web/` (**PWA**, `vite-plugin-pwa`, served from the root of one origin), and `shells/desktop/` (**Electron**). Scripts: `wallet:dev`, `wallet:build` (dev shell), `wallet:build:web`, `wallet:preview:web`, `wallet:smoke:pwa`, `wallet:icons`, `wallet:build:desktop`, `wallet:typecheck`, `wallet:smoke`, `wallet:smoke:desktop`, `wallet:smoke:portable`, `wallet:desktop`, `wallet:desktop:pack`, `wallet:portable`, `wallet:installer`, `wallet:dist`.
- **The PWA target is the one build whose `root` is not `wallet/`.** `vite --mode web` sets `root: shells/web`, so `dist/web` gets `index.html`, `sw.js` and `manifest.webmanifest` at its **root** — `vite-plugin-pwa` derives `navigateFallback`, scope and the precache list from the build root, and HTML under `dist/web/shells/web/` silently breaks navigation fallback. `base: '/'`, `outDir` absolute, and `preview.port: 5174` (the node's CORS allowlist is `:5173`/`:5174`; `vite preview`'s default 4173 is blocked, which shows up as a bogus "RPC offline"). `/rpc` must live on the same origin as the app, so no `VITE_RPC_URL` is needed.
- **PWA service worker is `prompt`, never `autoUpdate`.** `autoUpdate` forces `skipWaiting` + `clientsClaim` and reloads the tab itself, which would kill an in-flight transaction; the banner in `shells/web/PwaOverlay.tsx` is the only path that reloads. `injectRegister: null` (registration lives in `wallet/src/pwa/register.ts` so update state reaches React), `runtimeCaching: []` (caching RPC responses produces stale balances with no symptom), `navigateFallbackDenylist: [/^\/rpc/]`, `includeManifestIcons: false` (icons are already precached by `globPatterns`; the default `true` adds duplicate entries), and `devOptions.enabled: false` — in dev the plugin resolves `virtual:pwa-register` to a no-op, so `vite --mode web` still runs, but service worker/offline/install must be tested through `wallet:preview:web`. `wallet:smoke:pwa` (`wallet/scripts/pwaCheck.ts`) builds the target and asserts the artifacts: HTML at the dist root, iOS meta + `viewport-fit`, manifest fields, **PNG dimensions read from the IHDR** (not the filename), `sw.js` precaching every build file except itself/`workbox-*.js`, and no `/rpc` in the precache. Icons are generated once by `@vite-pwa/assets-generator` (two presets, `padding: 0`, committed output) and are not part of the build.
- **Two distribution shapes, and the portable one has a trap.** The NSIS installer stores the vault in `%APPDATA%\NexChain Wallet\wallet`. The **portable** `.exe` (electron-builder `portable` target) sets `PORTABLE_EXECUTABLE_DIR`, which `main.cjs` uses to relocate `userData` to `<exe folder>\NexChainWallet-Data\wallet`. Without that relocation a "portable" build still writes to `%APPDATA%`, so the wallet silently appears **lost** when the `.exe` is carried to another machine — no error, just an empty wallet. `bun run wallet:smoke:portable` guards this with three scenarios (no env → user profile; env + writable → relocated; env + unwritable → fallback without crashing). `app.setPath('userData', …)` must be called before `app.whenReady()`. The write probe deliberately keeps its `unlink` outside the critical `try`, so an antivirus holding the probe file cannot be mistaken for "folder not writable" — that false negative would strand a portable user's wallet.
- **`wallet/` runs without any `.env`.** Every value has a correct default: the node URL is set from the Settings screen at runtime, the explorer URL is empty (external links off), and the vault backend is injected by the shell. `wallet/vite.config.ts` pins `envDir` to the `wallet/` folder so Vite never picks up the root `.env`, which holds _node_ secrets (`NEX_CHAIN_ID`, bind host) unrelated to the wallet build. `wallet/.env.example` is documentation only — do not copy it.
- The Electron main process (`shells/desktop/electron/main.cjs`) is the only place that knows the vault path (`app.getPath('userData')/wallet`). Renderer security is `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, and only four vault operations cross the bridge. Vault keys are validated in the main process (lowercase `[a-z0-9._-]{1,64}`, resolved path must stay inside `walletDir`), writes are atomic (tmp → fsync → rename), and the NSIS uninstaller must **not** delete app data (`deleteAppDataOnUninstall: false`) — the vault holds funds.
- Desktop build gotcha: the `desktop` target sets `base: './'` in `vite.config.ts`. Without it, Vite emits `/assets/…`, which under Electron's `file://` resolves to the **drive root** and renders a blank window with no obvious error. If the Electron window is blank, check this first.
- `NEX_DISABLE_GPU=1` disables GPU acceleration. It must be set before any other `app.*` call in `main.cjs` (Chromium reads GPU switches when the GPU process is first prepared). Needed in display-less environments, where the GPU process crashes and Electron kills the whole app with `GPU process isn't usable. Goodbye.` — this reproduces on vanilla Electron too, so it is not an app bug. **`disable-gpu` alone is not enough on Electron 44**: Chromium still spawns a GPU process for compositing and that process still crashes and still kills the app. `disable-gpu-sandbox` is what actually stops it. Scripts that spawn Electron must also delete `ELECTRON_RUN_AS_NODE` from the child env, or `require('electron')` returns a path string and `app` is `undefined`.
- The desktop vault backend must be injected by the shell **before** first render (`getVault()` caches a promise singleton), and its files must live in the per-user data dir, never beside the executable (program dirs are read-only on Windows and may be wiped on update). See `wallet/shells/desktop/README.md`.
- `wallet-ext/` (the Chrome MV3 extension) was **deleted** — the extension is retired by decision, so its whole-directory vendor snapshot and `verify:independence` guard are gone. Do not reintroduce a snapshot: `wallet/` builds inside this repo, so it aliases root `src/` directly. Contact points that only existed for MV3 (`chrome.storage`, `rpcProxy`, service worker, content/inpage scripts) were removed with it.
