# AGENTS.md

## Project shape

- This is a Bun-run TypeScript blockchain node with no root workspace config. The root lockfile is intentionally ignored; `explorer/`, `wallet/`, and `miner-ui/` are independent Vite/React packages with their own `bun.lock`. Install the root, then run `bun install` in each UI directory.
- Despite the README's P2P wording, the implemented node network surface is HTTP JSON-RPC plus external miners; there is no `p2p/` implementation.
- `apps/node/server.ts` is the node entrypoint (`bun run rpc:start`, which runs `bun run apps/node/server.ts`) and serves JSON-RPC at `POST /rpc`; it attempts to create genesis on startup when the chain is empty. `apps/miner/miner.ts` is the runnable external miner (`bun run apps/miner/miner.ts`); `apps/miner/runMiner.ts` only exports `runMiner` and is not a CLI entrypoint.
- The shared/core modules now live under `src/`: `src/core/` (the blockchain engine — was `nexchain/`), `src/wallet/` (accounts — was `account/`), `src/crypto/` (key + sign), `src/client/`, `src/types/` (was `interface/`), `src/logging/`, and `src/rpc/`. Runnable apps live under `apps/`: `apps/node/` (the node) and `apps/miner/` (the standalone miner). `explorer/` (Vite port 5173), `wallet/` (port 5174), and `miner-ui/` (port 5175) are independent frontends; the root `tsconfig.json` excludes all three.
- There is no wired top-level wallet-bootstrap command: `nex_createWallet` exists, but ensure the node wallet file (`wallet/main.json` by default) exists before expecting genesis or mining to work.
- Mining is intentionally outside the node: the miner gets `nex_getWork`, hashes the payload and nonce, then submits `nex_submitWork`; the node verifies the work and signs with its own wallet. The miner needs only the RPC URL and reward address. `apps/miner/miner.ts` is intentionally standalone and duplicates the difficulty, hash, and address rules; synchronize it manually with the canonical `src/core/` modules when those rules change. `miner-ui/` is the browser counterpart and does the opposite: it aliases the canonical `src/core/consensus/Pow` (`hashWithNonce`) and `src/core/consensus/difficulty` (`meetsDifficulty`), so its hash is guaranteed identical to the node's re-verification, and runs the PoW loop in a Web Worker (`miner-ui/src/workers/miner.worker.ts`) so the UI never blocks.

## Commands

- `bun run check` is the root `bunx tsc` typecheck, then deletes `dist` on success; `bun run build` emits root `dist`. Neither runs the regression gates or either UI.
- Core gates: `bun run check:browser`, `bun run check:tx`, `bun run check:wallet`, `bun run check:difficulty`, and `bun run check:pow`. The browser gate checks bundling, tx/difficulty are offline, and the wallet gate uses memory plus `fake-indexeddb` without needing a node. `check:pow` proves `PowHasher` (the fixed-buffer PoW hot path) is byte-for-byte identical to `hashWithNonce` and to `node:crypto`, including UTF-8/non-ASCII payloads and huge nonces. `check:tx` asserts the localhost default, so unset `NEX_RPC_URL` (including a value loaded from `.env`) before running it. `check:browser` ends with POSIX `rm -f`; verify cleanup on Windows if the shell does not provide it. `bun run pow:bench` is a diagnostic (not a gate) that compares old-vs-new hash paths and suggests a worker count for the current machine.

## PoW hot path

- The mining loop is the one place where hashing cost matters, so the canonical modules expose a bulk API: `createPowHasher(payload).hash(nonce)` (in `src/core/encoding/sha256.ts`, re-exported from `src/core/consensus/Pow.ts`). It encodes the payload once and writes each nonce into a fixed buffer, avoiding the per-iteration string concat in `hashWithNonce`. Use `hashWithNonce` for one-off hashing only (e.g. node re-verification); use `createPowHasher` inside any mining loop.
- Never replace `Math.floor(n / 10)` with `(n / 10) | 0` when formatting a nonce: `| 0` forces int32 and silently corrupts nonces >= 2^31. `check:pow` guards this with `Number.MAX_SAFE_INTEGER`.
- `miner-ui` partitions the nonce space across N Web Workers by stride (`startNonce = i`, `nonceStride = N`), so workers never overlap and need no central coordination; the first to find a solution wins. Worker count comes from `navigator.hardwareConcurrency` clamped to 4, overridable via `localStorage['nex_miner_workers']`. Throughput saturates at 2–3 workers on small CPUs — more workers can be slower, so calibrate with `bun run pow:bench` rather than assuming more is better.
- `apps/miner/miner.ts` stays single-file and dependency-free on purpose, so it inlines its own fixed-buffer hasher and self-checks it against `hashWithNonce` at startup. Keep that copy in sync with `PowHasher` when the nonce-formatting rule changes.
- Frontends: `bun run explorer:dev`, `bun run explorer:build`, `bun run --cwd explorer typecheck`, `bun run --cwd explorer audit:ui`, `bun run --cwd explorer smoke`; `bun run wallet:dev`, `bun run wallet:build`, `bun run wallet:typecheck`, `bun run wallet:smoke`; and `bun run miner:dev`, `bun run miner:build`, `bun run miner:typecheck`, `bun run miner:smoke`. UI `build` scripts run `tsc --noEmit` before Vite; `audit:ui` is static contrast/class coverage. `explorer smoke` needs a live RPC with at least five blocks; `wallet:smoke` is local and does not touch LevelDB or send transactions. `miner:smoke` (`scripts/minerUiSmoke.ts`) is the opposite of local — it needs a live node and mutates it (creates a wallet, mines one block, credits a reward).
- There is no `test` or `lint` script/framework, and the Husky pre-commit hook is only a shebang (there are no GitHub workflows). `scripts/vaultBench.ts` is a benchmark, not a correctness test; `scripts/e2ePostRemoval.ts` mutates a funded live node (mempool, balances, and chain) and currently spawns a missing `mine.ts`, so neither is a routine check.
- Formatting is `bun run format` (Prettier: tabs, no semicolons, single quotes, trailing commas, width 80); use focused `bunx prettier --write <files>` when possible.

## RPC contracts

- RPC results are deliberately heterogeneous: legacy account/state methods return hex-encoded JSON, `nex_getBalance` returns a hex string, `nex_getChainId` is numeric, and newer explorer/mempool methods return plain JSON. When adding or changing a method, update the matching decoder in `explorer/src/api/methods.ts` and the relevant smoke coverage.
- Two traps worth repeating for miner clients: `nex_getAccount` returns hex **with a `0x` prefix**, so decode it with `hexToString`/`decodeHexJson` — `Buffer.from(hex, 'hex')` silently yields an empty string because it stops at `x`. `nex_getWork`/`nex_submitWork` return plain JSON, and `nex_getWork` echoes `minerAddress` plus an `expiresAt` epoch-ms the client should count down (`JOB_TTL_MS` is 5 minutes in `src/core/consensus/jobStore.ts`).

## Runtime and data

- Copy the root `.env.example` to `.env`. `apps/node/server.ts` loads the working-directory `.env`; `NEX_RPC_PORT` (or `PORT`) defaults to 8000; `RPC_BIND_HOST` is *documented* as defaulting to `127.0.0.1`, but `apps/node/server.ts` actually falls back to `0.0.0.0` when it is unset (`process.env.RPC_BIND_HOST as string || '0.0.0.0'`) — set it explicitly when a localhost-only node is intended. Use `0.0.0.0` only when another LAN host must reach the RPC.
- The shared Node/Bun client and `apps/miner/runMiner.ts` use `NEX_RPC_URL` (default `http://localhost:8000/rpc`); `apps/miner/miner.ts` ignores that variable and always prompts for its URL. Vite apps use build-time `VITE_RPC_URL`; wallet also accepts optional `VITE_EXPLORER_URL` (or a Settings/localStorage override) for confirmed transaction links. Explorer requires `explorer/.env`; wallet env is optional, with runtime priority `localStorage` override → `VITE_RPC_URL` → page-host fallback; `miner-ui` uses the same priority under the key `nex_miner_rpc_url`.
- Level stores live under the data directory resolved by `NEX_DATA_DIR` (default `./data`, relative to the working directory), one LevelDB per store: `{block,history,memPool,state,storeData}`. The path is deliberately anchored to `process.cwd()` and **not** to `__dirname` (see `src/core/state/db/dataDir.ts`): a source-relative path silently relocates the chain when the code moves or is bundled, and it puts chain data inside the source tree. `initFile()` is fail-closed — it probes writability and throws rather than letting the node start against a data directory it cannot write. Do not commit `data`, `wallet`, `config`, `logs`, or `dist`; `wallet/<primary>.json` contains the node mnemonic.
- **Name collision to watch for:** the ignored `wallet/` directory is the *node's* mnemonic store (`wallet/main.json`), and it is unrelated to the `wallet/` UI package. The `.gitignore` entry for `wallet` is anchored deliberately (see `.gitignore`) so it does not swallow the UI package. When editing either, be explicit about which one you mean.
- The node wallet is file-based: `config/wallet.conf.json` selects the primary wallet (default `main`). Genesis creation and successful work submission require that wallet; RPC can still start without it, but the chain may remain empty.

## Shared browser code

- `wallet` and `miner-ui` alias the backend modules through their `vite.config.ts` (`ROOT_MODULES` maps `src/core`, `src/crypto`, `src/wallet`, `src/types`, `src/client`, `src/rpc`, `src/logging`) rather than duplicating crypto and transaction logic. When a new backend module under `src/` must be consumed by a UI, add it to that app's `ROOT_MODULES` and to its `tsconfig.json` `paths`.
- New contributors should start with `docs/LEARNING_PATH.md`; each module carries a short `README.md` explaining its responsibility and entry points.
- Keep shared browser imports free of Node built-ins; `bun run check:browser` is the guard. Keep `wallet/src/polyfill.ts` imported before wallet modules, preserve the Vite `buffer` alias, and use named `bip39` imports (the default import breaks Vite interop).
- Wallet amounts use `formatNxcCompact()`/`AmountDisplay` for primary UI; keep exact nexu values only behind the detail disclosure so mobile layouts stay readable.

## wallet/ — one codebase, several shells

- `wallet/` is not a single app. `wallet/src/` is the shared source (nine screens, `ui/`, `lib/`, `workers/`) and `wallet/shells/` holds the entry points. `wallet/src/lib/vaultStore.ts`, `deviceCrypto.ts`, and `rpcUrl.ts` are the **three injection points** where shells differ; the screens never branch on platform. Adding a shell means writing a new entry under `shells/` that injects a `WalletKV`, a device class, and an RPC default, then renders the shared `App`.
- Shells: `shells/dev/` (Vite port 5174, `VITE_VAULT_BACKEND=memory`, for working on the UI) and `shells/desktop/` (**Electron**). Scripts: `wallet:dev`, `wallet:build` (dev shell), `wallet:build:desktop`, `wallet:typecheck`, `wallet:smoke`, `wallet:smoke:desktop`, `wallet:smoke:portable`, `wallet:desktop`, `wallet:desktop:pack`, `wallet:portable`, `wallet:installer`, `wallet:dist`.
- **Two distribution shapes, and the portable one has a trap.** The NSIS installer stores the vault in `%APPDATA%\NexChain Wallet\wallet`. The **portable** `.exe` (electron-builder `portable` target) sets `PORTABLE_EXECUTABLE_DIR`, which `main.cjs` uses to relocate `userData` to `<exe folder>\NexChainWallet-Data\wallet`. Without that relocation a "portable" build still writes to `%APPDATA%`, so the wallet silently appears **lost** when the `.exe` is carried to another machine — no error, just an empty wallet. `bun run wallet:smoke:portable` guards this with three scenarios (no env → user profile; env + writable → relocated; env + unwritable → fallback without crashing). `app.setPath('userData', …)` must be called before `app.whenReady()`. The write probe deliberately keeps its `unlink` outside the critical `try`, so an antivirus holding the probe file cannot be mistaken for "folder not writable" — that false negative would strand a portable user's wallet.
- **`wallet/` runs without any `.env`.** Every value has a correct default: the node URL is set from the Settings screen at runtime, the explorer URL is empty (external links off), and the vault backend is injected by the shell. `wallet/vite.config.ts` pins `envDir` to the `wallet/` folder so Vite never picks up the root `.env`, which holds *node* secrets (`NEX_CHAIN_ID`, bind host) unrelated to the wallet build. `wallet/.env.example` is documentation only — do not copy it.
- The Electron main process (`shells/desktop/electron/main.cjs`) is the only place that knows the vault path (`app.getPath('userData')/wallet`). Renderer security is `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, and only four vault operations cross the bridge. Vault keys are validated in the main process (lowercase `[a-z0-9._-]{1,64}`, resolved path must stay inside `walletDir`), writes are atomic (tmp → fsync → rename), and the NSIS uninstaller must **not** delete app data (`deleteAppDataOnUninstall: false`) — the vault holds funds.
- Desktop build gotcha: the `desktop` target sets `base: './'` in `vite.config.ts`. Without it, Vite emits `/assets/…`, which under Electron's `file://` resolves to the **drive root** and renders a blank window with no obvious error. If the Electron window is blank, check this first.
- `NEX_DISABLE_GPU=1` disables GPU acceleration. It must be set before any other `app.*` call in `main.cjs` (Chromium reads GPU switches when the GPU process is first prepared). Needed in display-less environments, where the GPU process crashes and Electron kills the whole app with `GPU process isn't usable. Goodbye.` — this reproduces on vanilla Electron too, so it is not an app bug. **`disable-gpu` alone is not enough on Electron 44**: Chromium still spawns a GPU process for compositing and that process still crashes and still kills the app. `disable-gpu-sandbox` is what actually stops it. Scripts that spawn Electron must also delete `ELECTRON_RUN_AS_NODE` from the child env, or `require('electron')` returns a path string and `app` is `undefined`.
- The desktop vault backend must be injected by the shell **before** first render (`getVault()` caches a promise singleton), and its files must live in the per-user data dir, never beside the executable (program dirs are read-only on Windows and may be wiped on update). See `wallet/shells/desktop/README.md`.
- `wallet-ext/` (the Chrome MV3 extension) was **deleted** — the extension is retired by decision, so its whole-directory vendor snapshot and `verify:independence` guard are gone. Do not reintroduce a snapshot: `wallet/` builds inside this repo, so it aliases root `src/` directly. Contact points that only existed for MV3 (`chrome.storage`, `rpcProxy`, service worker, content/inpage scripts) were removed with it.
